# خطة تنفيذ MediTrack

المرجع التفصيلي للقرارات والعقد بين الواجهة والـ Backend: [`Meditrack-Front/BACKEND_HANDOFF.md`](../Meditrack-Front/BACKEND_HANDOFF.md).

## قواعد عامة لكل المراحل

- كل مطوّرة مسؤولة عن الـ **Backend والـ React والـ Mock** لميزات مسارها.
- **Developer A: المخزون والعمليات.** المخزون، والعمليات، والتعديلات، والـ Dashboard، والتقارير.
- **Developer B: الحسابات والأصناف والمنصة.** الدخول، والمستخدمون، والأصناف، والشركات والباركود، والأرشفة، والتنبيهات، والتصدير.
- **متى تُعتبر الميزة منتهية:**
  - الـ Backend يعمل، ومعه اختباراته.
  - الواجهة مربوطة بالـ API.
  - الـ Mock يطبّق نفس القواعد.
  - BACKEND_HANDOFF.md يطابق ما بُني.
- **الانتقال إلى المرحلة التالية** يكون بعد أن تتحقق "النتيجة المطلوبة" للمرحلة الحالية، وليس حسب موعد.

## المرحلة 2: الدخول وقلب المخزون

| Developer A | Developer B |
|---|---|
| **StockService**: المتوسط المرجّح، وإعادة حساب المخزون، ومنع المخزون السالب | **الشركات المصنعة**: `GET /manufacturers` للـ autocomplete (دالة `resolve()` جاهزة من المرحلة 1) |
| ربط الـ Seeder بـ StockService | **Authentication**: Login، وRemember me، وLogout، و`/me` |
| **Incoming**: إنشاء الدفعة، والشركة، وتاريخ الإنتاج، والمورّد الاختياري | **Account Expiry**: منع الدخول، ورفض الـ tokens |
| React: نموذج Incoming (حقل الشركة مع autocomplete، وتاريخ الإنتاج، وعلامات `*` و"(optional)") | **Users & Permissions**: صلاحيات الأدوار، وإدارة المستخدمين |
| | React: Remember me في Login، وحقل تاريخ انتهاء الحساب وشارة "Expired" في Users |

**مهام مشتركة:**

- ربط Incoming بخدمة الشركات المصنعة: A تستدعي `ManufacturerService::resolve()` الجاهزة.
- تشغيل الواجهة على الـ API بدل الـ Mock.

**النتيجة المطلوبة:**

- ✅ تسجيل دخول حقيقي من الواجهة، والحساب المنتهي أو المعطّل لا يدخل
- ✅ تسجيل Incoming من الواجهة يحدّث المخزون والمتوسط المرجّح بشكل صحيح

## المرحلة 3: المخزون والأصناف كاملة

| Developer A | Developer B |
|---|---|
| **Outgoing**، مع دفعات الشركة المختارة أولًا | **Categories** |
| **Expiry & Disposal** | **Items**: الإنشاء والتعديل، والتفاصيل الست |
| قوائم العمليات والبحث فيها | **Manufacturers & Barcodes**: الربط، والحذف، والبحث بالباركود |
| React: صفحة Transactions ونموذج Outgoing على الـ API | **Archive History**: سبب الأرشفة، والسجل، والاستعادة |
| | **Profile & Settings** |
| | React: نافذة Item Details، ومكوّن المسح (Scanner والكاميرا)، ونافذة سبب الأرشفة وسجلها |

**مهام مشتركة:**

- **مكوّن المسح:** B تبنيه، وA تضيفه إلى نموذجي Incoming وOutgoing.
- **قاعدة "لا أرشفة مع وجود مخزون":** B تبنيها، وA تتأكد معها أن الكميات صحيحة.
- **زر Dispose في نافذة Item Details:** النافذة لـ B، ومنطق الإتلاف لـ A.

**النتيجة المطلوبة:**

- ✅ صفحتا Inventory وTransactions تعملان بالكامل على الـ API
- ✅ مسح الباركود يختار الصنف والشركة، والباركود غير المعروف يمكن ربطه
- ✅ الأرشفة تتطلب سببًا، وسجلها يظهر

- استدعاؤها كذلك عند تغيير تاريخ انتهاء الحساب أو حالته.

**النتيجة المطلوبة:**

- ✅ التعديل والإلغاء يعيدان حساب المخزون بأمان، والتعديلات تظهر في History

## ملخص التوزيع

| | Developer A | Developer B |
|---|---|---|
| **المرحلة 2** | StockService، وIncoming | الشركات المصنعة، وAuth، وAccount Expiry، وUsers |
| **المرحلة 3** | Outgoing، وDisposal، والقوائم | Categories، وItems، والباركود، والأرشفة، وProfile |
| **المرحلة 4** | Edit، وCancel، وRevisions | Notifications، والأولوية |
| **المرحلة 5** | Dashboard، وReports | Export، وسجل التصدير |

**عن التوازن:** مسار A أعمق، لأن فيه منطق المخزون الحساس. مسار B فيه عدد أكبر من الميزات، لكنها أبسط وأكثر استقلالًا. لذلك حجم العمل متقارب.

**ما ينتظره كل مسار من الآخر:**

- **A لا تنتظر B في شيء:** `ManufacturerService::resolve()` بُنيت في المرحلة 1، و`NotificationService` تُستدعى من اليوم الأول (فارغة حتى المرحلة 4).
- **B تنتظر من A** `ReportService::build()` في المرحلة 5 فقط: شكل النتيجة (`ReportResult`) ثابت من المرحلة 1، فتبني B التصدير على نتيجة تجريبية بنفس الشكل.
- **كل ما عدا ذلك يُنفَّذ بالتوازي.** A تعمل على الأصناف الموجودة في الـ Seeder، فلا تحتاج أن تنتظر Items API.
